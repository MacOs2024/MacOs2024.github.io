# Обязательные правила VoltCalc

Единый источник правил для всех, кто вносит изменения в этот репозиторий —
людей и ИИ-агентов. `AGENTS.md` и `CLAUDE.md` ссылаются сюда и ничего не
дублируют.

## Процесс

1. **Никогда не push напрямую в `main`.** Изменения идут только через pull
   request. Это правило проекта действует независимо от настроек GitHub.
   Серверную защиту `main` нужно включить и проверить отдельно: наличие этого
   файла само по себе не блокирует прямой push, force-push или удаление ветки.
2. **Начинать от свежего `origin/main`.** Перед работой: `git fetch origin`,
   затем ветка от актуального `origin/main`.
3. **Одна задача = одна ветка = один основной исполнитель.** Параллельная
   работа двух агентов в одной ветке приводит к откатам и дублям.
4. **Публикация зависит от тестов.** Job `deploy` запускается только после
   зелёного job `test`. Не разъединять их обратно на независимые workflow.

## Инженерная достоверность

5. **Формула не меняется без первоисточника, его редакции и эталонного
   теста.** В карточке источника на странице указываются документ,
   организация, редакция, раздел и дата обращения.
6. **Нормативный вердикт запрещён при недостаточных исходных данных.** Если
   входных данных не хватает для однозначного вывода, статус должен быть
   «недостаточно данных», а не «проходит». Расчёт не должен звучать
   категоричнее, чем позволяет физика и исходники.
7. **Каждый режим интерфейса обязан влиять на расчёт.** Переключатель,
   который не меняет результат, — дефект: либо он реализован, либо удалён
   из UI.
8. **Спорную нормативную формулу помечать как блокирующую.** Если редакция,
   область применения или исходные данные не определены однозначно, расчёт
   отключается либо переводится в оценочный режим без нормативного вердикта.
   Формальное подтверждение владельца для продолжения работы не требуется.

## Кодовая база

9. **Менять источник в `generator/`, затем пересобирать.** Сгенерированные
   HTML вручную не редактировать: следующая сборка затрёт правку.
   Обязательна проверка `python3 generator/build.py && git diff --exit-code`.
10. **Сохранять работающую основу.** Строгий числовой ввод, экспорт в PDF,
    печатная шапка, Яндекс.Метрика согласно принятому privacy-решению,
    sitemap, robots, canonical, favicon и файлы верификации поисковых
    систем не должны пропадать при рефакторинге.
    Принятое решение для Метрики (владелец проекта, 13.08.2026): счётчик
    `111301996` загружается на всех страницах каталога сразу, без баннера
    согласия. Вариант с предварительным согласием рассматривался и отклонён
    как избыточный для русскоязычной аудитории сайта. Обязательные условия
    этого решения: `webvisor` и `clickmap` выключены явно, запись сессий не
    ведётся, страница политики счётчика не содержит, а сама политика
    перечисляет состав собираемых данных, обработчика и способы отказа.
    Менять состав собираемых данных, не обновив политику, запрещено.

## Тесты и приёмка

11. **Обязательны перед PR:** `npm ci`, `npm test`, `python3
    generator/build.py`, `git diff --exit-code`, `npx playwright test`,
    `npm audit`.
    Если в окружении уже стоит Chromium другой сборки и скачивать браузер
    нельзя, путь к нему передаётся явно, иначе Playwright ищет свою сборку и
    падает на `Executable doesn't exist`:
    `PW_CHROMIUM_PATH=/opt/pw-browsers/chromium-<сборка>/chrome-linux/chrome npx playwright test`.
    В CI переменная не нужна — там браузер ставится штатно.
12. **Число тестов — не доказательство корректности формул.** В отчёте
    приводить разбивку: structural / functional / boundary / browser.
    Ожидаемые значения в тестах вычислять независимо от кода страницы, а не
    тем же алгоритмом. Наличие одного smoke-сценария не даёт права называть
    калькулятор инженерно проверенным: для статуса `agent-reviewed` или
    `verified` нужны минимум два независимых эталона, все режимы интерфейса,
    границы, неверный ввод, округление и отдельная проверка рискованного
    вердикта. Coverage guard подтверждает только наличие теста, не формулу.
13. **Не добавлять новые калькуляторы, пока не закрыты задачи P0 и P1** из
    аудита. Рост количества расширяет поверхность ответственности быстрее,
    чем растёт покрытие проверками.
14. **В PR перечислять:** какой риск закрыт, источник для каждой изменённой
    формулы, какие тесты добавлены, результат живой проверки и остаточные
    риски.

## Реестр инженерной проверки

Статусы расчётов ведутся в `ENGINEERING_AUDIT.md`:

- `verified` — формула подтверждена первоисточником, независимым вторым
  источником или контрольным примером и полной матрицей тестов;
- `agent-reviewed` — формула сверена с указанным первоисточником и покрыта
  эталонными тестами, но независимая вторая проверка ещё не выполнена;
- `estimate` — физическая оценка с явно показанными допущениями, без
  нормативного обещания;
- `pending` — не публиковать в каталоге либо отключить расчёт до проверки.

Поле «проверил» указывает фактического проверяющего и основание проверки.
Имя владельца нельзя указывать без его реального инженерного просмотра, но
отсутствие такого просмотра само по себе не блокирует статус
`agent-reviewed` и дальнейшую работу.
